# Performance and memory optimizations, 2026-11-20

Plum's language (Swift) and parts (libghostty-vt, Metal, the terminal host) stayed as they were; the costs Plum's own code could cut were found and cut. All measurements were on the same Mac (M4 Pro, macOS 26.3.1). Someone was working on that Mac, so the full measurement that brings windows to the front (`bench/run.py`, [2026-11-17](2026-11-17.md)) wasn't run again; measurements ran without a screen and with a test copy of the app in the background.

## Conclusions

- **Building a frame got 2.5–3.6× cheaper.** Under a flood of output every frame rebuilds every row, and the main-thread CPU for that on a 122×46 screen went from 0.30–0.87ms to 0.10–0.33ms. The drawn result is the same, pixel for pixel.
- **Parsing TUIs that use synchronized output (DEC 2026) got 17% faster** (190 → 222MB/s, by CPU time). That's how agents like Claude Code redraw their screen.
- **On the real path (reading through the terminal host, drawing at 120Hz)** throughput went up 10–24% and CPU per byte went down 0–17%. After that, a change in how output is read (below, "Reading output") made plain text 1.8× faster (170 → 299MB/s).
- **At the same time and in the same conditions, faster than Ghostty 1.4.0 on all 7 kinds** (11/23, below, "Taking turns with Ghostty 1.4.0"). With each app brought to the front for its turn so both drew, the median of the per-round ratios was 1.05–2.64×.
- **Because of App Nap, output throughput was 2–6× slower while the window was covered.** Plum now keeps macOS from putting it to sleep when covered. Speed holds while agents run and you work in another app.
- **Most of the memory belongs to macOS and the GPU driver.** While drawing, the GPU driver holds about 96MB; that doesn't depend on window size and appears even when drawing one empty render pass. A few seconds after output stops, the system takes it back. Plum's own heap is about 22MB with 7 tabs.

## Reading output (added the same afternoon)

A pty gives at most 1KB per read, whatever the baud (checked in C at 9600–230400). So under a flood of output it's a race of hundreds of thousands of reads a second, and the time to wake from a blocking read each time set the speed. The reading thread was made non-blocking: while output keeps coming it keeps reading without sleeping, and when the pty is empty it tries reading for up to 20µs more before sleeping in poll(2) (`TerminalIO.readOutput`).

- Reading the same pty from C: blocking read 147–197MB/s, this way 280–345MB/s. CPU per byte is about the same.
- Checking with poll(2) (timeout 0) during that extra look was slower instead (134–142). So it checks with read.
- The terminal host batches what comes in back to back and sends it to the app at once (on a pause, at 64KB, or after 2ms). The app parses as it reads. Batching on the app side too filled the pty while one batch was being parsed, and scrolling output slowed (81 → 60MB/s).
- Being non-blocking, a write can return "try again later" (EAGAIN). Every write now waits until there's room. `TerminalHostTests` checks that a 1MB paste and 3MB of output arrive complete (and was confirmed to fail when writes don't wait).

Before and after the change in the same conditions (reading through the host and drawing, no screen; median of 5 runs, MB/s):

|---|---|---|
| ascii | 170 | 299 |
| sync_tui | 167 | 207 |
| dense_cells | 210 | 248 |
| scrolling | 97 | 107 |

## App Nap and SIGPIPE (11/20 evening)

- **App Nap.** When a window is covered by others, macOS puts the app to sleep (App Nap) and slows its threads. In the covered test copy, output throughput was cursor_motion 87–99, ascii 187–214 and scroll_region 16–22MB/s; with App Nap turned off for that app alone it came back to 229–243, 266–322 and 108–113MB/s. A terminal keeps running agents and builds while its window is covered, so at launch the app asks not to be put to sleep, with `ProcessInfo.beginActivity(.userInitiatedAllowingIdleSystemSleep)`. Idle CPU was close to 0 to begin with and doesn't go up, and the Mac can still go to sleep. Checked with the window minimized (scroll_region 95–110, cursor_motion 209–244, ascii 310–324MB/s).
- **SIGPIPE.** When whoever sent a debug command closed the connection before reading the answer, the app ended without a trace (exit code 141). The committed version did the same. The app now ignores SIGPIPE as the terminal host does, so such a write fails with EPIPE and moves on.

## Taking turns with Ghostty 1.4.0 (11/23)

The official Ghostty 1.4.0 (notarization checked) and Plum's test copy were measured in turns on the same Mac (macOS 26.7.1) with the same data. Grid 122×46, Menlo 13. Ghostty was kept from reading the user's config. For each kind, 1 warm-up round, then 6 rounds; the app going first switched every round, with a 1.5s rest before each run. Each app was brought to the front for its turn, so both drew (with the user's permission, the Mac wasn't used meanwhile).

- Within a round, the app going second tended to come out slower (the first app was still drawing what was left on screen), so the ratio of the two was taken per round.
- When a moment of the whole system getting busy fell on one side's turn, that round alone jumped (ratios of 0.46–0.50 when it hit Plum alone, 2.14 when it hit Ghostty alone). ## What changed

| What | Where | Effect |
|---|---|---|
| Getting a row's cells in one go (`ROW_DATA_CELLS_RAW`). The cells' bit layout is read once from the description the library provides (`ghostty_type_json`) and decoded directly. Without a description, it asks field by field as before | `TerminalRenderer.buildRow`, `CellLayout` | 6–8 C calls per cell → 0 for default-color text |
| No color or style lookups for default-style text. While the style stays the same, the previous cell's values are used | Same place | Calls only for colored cells |
| Glyph lookup: an array index for ASCII; everything else goes through a 4096-slot hash cache before the dictionary | `GlyphAtlas.entry` | Dictionary hashing was the largest part of the frame cost |
| Rows rebuilt in place (no array reallocation), cluster buffer reused | `buildRow` | Fewer allocations and retain/release |
| The whole-screen copy made every time synchronized output started now happens once per 8ms (one screen refresh) | render hold in `TerminalSession` | Thousands per second → at most 120 |
| Reading the cell layout description (about 2ms) moved from the first frame to the background right after launch | `AppDelegate` | First-frame delay gone |

## The real path: reading through the host and drawing

`RenderSpeedTests.testThroughputWhileDrawing` with `PLUM_BENCH_HOST=1`. A terminal host starts inside the test process, and while program output comes in through the host's socket, the main thread draws to an offscreen Metal layer at up to 120Hz. Before and after were measured in turns at the same time of day, 5 runs each (median).

| Data | Throughput (before → after) | CPU per byte (before → after) |
|---|---|---|
| ascii | 143 → 171MB/s | 7.60 → 6.81s/GB |
| dense_cells | 173 → 214MB/s | 9.57 → 7.94s/GB |
| unicode | 176 → 194MB/s | 12.76 → 12.59s/GB |
| sync_tui | 157 → 173MB/s | 10.60 → 9.79s/GB |

- unicode's CPU barely changed because most of it is the cost of drawing characters seen for the first time (rasterizing).
- The host's reading thread spends most of its time in system calls (reading the pty, writing the socket, the `ioctl` that checks for bytes left). The `ioctl` is about 8% of that thread; removing it would mean making the pty non-blocking, with a risk of losing input on large pastes, so it was left.
- Under a flood of output, the time the main thread waited while building a frame (the terminal lock included) averaged 0.06ms, 0.35ms at most. There was no need to split parsing into smaller pieces.

## Memory

Measured with the test copy in the background (window 1180×760pt, 2× scale, 7 tabs), by `footprint`.

| State | Total | GPU driver's share |
|---|---|---|
| Drawing output continuously | 168MB | 98MB |
| 6s after output stops | 70MB | 2MB |

- **The GPU memory while drawing isn't Plum's.** With the window shrunk to 800×500 or grown to 1600×1000, it stayed the same at 98–100MB. A small program that draws nothing but one empty render pass with Metal also went from 4MB to 111MB, and to 80MB with a compute shader instead of a render pass. It looks like working memory the Apple GPU driver holds while rendering, and the system takes it back when output stops. Rewriting the renderer with compute would save only 33MB, so it wasn't done.
- **What's left after output stops scales with window size** (55MB at 800×500, 88MB at 1600×1000): the visible terminal's 2 drawing buffers (already set to the minimum, 2) and the window itself.
- **Plum's heap is about 22MB** (7 tabs). The big parts are SwiftUI and AppKit internals, Swift metadata and the engine's pages. Making one terminal costs under 1MB. Scrollback uses up to 10MB per tab (a setting; the default is the same as Ghostty's).
- Idle CPU with 7 tabs was about 30ms per 20s, mostly the system calls that check each tab's programs and ports every 2s.

## How to measure again

```sh
python3 bench/gen-data.py <folder> 122 46        # about 270MB
PLUM_BENCH_DATA=<folder> swift test -c release -Xswiftc -enable-testing --filter "RenderSpeedTests/testFrameCost"
PLUM_BENCH_DATA=<folder> swift test -c release -Xswiftc -enable-testing --filter "PtySpeedTests/testParseSpeed"
PLUM_BENCH_HOST=1 PLUM_BENCH_DATA=<folder> PLUM_BENCH_RUNS=5 swift test -c release -Xswiftc -enable-testing --filter "RenderSpeedTests/testThroughputWhileDrawing"
```

- Pick data kinds with, for example, `PLUM_BENCH_SETS=ascii,sync_tui`. Throughput swings with system load, so it's best to measure before and after in turns at the same time of day. Frame cost and parsing speed swing little.
- `CellLayoutTests` checks every time that the screen cell decoding matches the library (it's part of the normal tests).
