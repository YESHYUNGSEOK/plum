# 성능·메모리 최적화 — 2026-11-20

Plum의 언어(Swift)와 구성(libghostty-vt, Metal, 터미널 호스트)은 그대로 두고, Plum 쪽 코드에서 줄일 수 있는 비용을 찾아 줄였다. 측정은 모두 같은 Mac(M4 Pro, macOS 26.3.1)에서 했다. 사용자가 같은 Mac을 쓰는 중이라 창을 앞으로 가져오는 전체 측정(`bench/run.py`, [2026-11-17](2026-11-17.md))은 다시 돌리지 않았고, 화면 없이 도는 측정과 뒤에 띄운 테스트 앱으로 쟀다.

## 결론

- **프레임 하나를 만드는 비용이 2.5~3.6배 줄었다.** 출력이 쏟아질 때는 매 프레임 모든 줄을 다시 만드는데, 그 메인 스레드 CPU가 122×46 화면에서 0.30~0.87ms에서 0.10~0.33ms가 됐다. 그린 결과는 픽셀 단위로 같다.
- **동기화 출력(DEC 2026)을 쓰는 TUI의 파싱이 17% 빨라졌다**(190 → 222MB/s, CPU 기준). Claude Code 같은 에이전트가 화면을 다시 그릴 때 쓰는 방식이다.
- **실제 경로(터미널 호스트를 거쳐 읽고, 120Hz로 그리기)에서** 처리량은 10~24% 늘고, 바이트당 CPU는 0~17% 줄었다. 그 뒤 출력 읽기 방식을 바꿔(아래 "출력 읽기") 일반 텍스트는 1.8배(170 → 299MB/s)가 됐다.
- **같은 시간, 같은 조건에서 Ghostty 1.4.0보다 7종류 모두 빠르다**(11/23, 아래 "Ghostty 1.4.0과 번갈아 재기"). 두 앱을 차례마다 맨 앞에 두고 그리게 했을 때 라운드별 비율의 중앙값이 1.05~2.64배다.
- **App Nap 때문에, 창이 가려져 있으면 출력 처리가 2~6배 느렸다.** macOS가 가려진 앱을 재우던 것을 Plum이 막게 했다. 에이전트를 돌려 두고 다른 앱에서 일할 때 그대로다.
- **메모리는 대부분 macOS와 GPU 드라이버 몫이다.** 그리는 동안 GPU 드라이버가 약 96MB를 잡는데, 이는 창 크기와 상관없고 빈 렌더 패스 하나만 그려도 생긴다. 출력이 멈추고 몇 초 지나면 시스템이 거둬 간다. Plum 자신의 힙은 탭 7개에 약 22MB다.

## 출력 읽기 (같은 날 오후에 추가)

pty는 baud와 상관없이 한 번 읽을 때 최대 1KB만 내준다(C로 9600~230400을 확인). 그래서 출력이 쏟아질 때는 초당 수십만 번의 읽기 경쟁이고, 블로킹 read에서 매번 깨어나는 시간이 속도를 정했다. 읽는 스레드를 논블로킹으로 바꿔, 출력이 이어지는 동안에는 잠들지 않고 계속 읽고, 비어 있으면 최대 20µs 더 읽어 본 뒤에야 poll(2)에서 잠들게 했다(`TerminalIO.readOutput`).

- C로 같은 pty를 읽어 본 결과: 블로킹 read 147~197MB/s, 이 방식 280~345MB/s. 바이트당 CPU는 거의 같다.
- 다시 보는 동안 poll(2)(대기 0)로 확인하면 오히려 느렸다(134~142). 그래서 read로 확인한다.
- 터미널 호스트는 이어서 들어온 것을 묶어 앱에 한 번에 보낸다(쉼이 오거나, 64KB가 차거나, 2ms가 지나면). 앱은 읽는 대로 바로 파싱한다. 앱 쪽까지 묶으면, 묶음 하나를 파싱하는 동안 pty가 가득 차 스크롤 출력이 81 → 60MB/s로 느려졌다.
- 논블로킹이 되어 쓰기가 "나중에 다시"(EAGAIN)를 돌려줄 수 있다. 쓰기는 모두 자리가 날 때까지 기다리게 했다. 1MB 붙여넣기와 3MB 출력이 빠짐없이 가는지를 `TerminalHostTests`가 확인한다(기다리지 않게 바꾸면 실패하는 것을 확인했다).

같은 조건(호스트를 거쳐 읽고 그리기, 화면 없이)에서 바꾸기 전과 후(5회 중앙값, MB/s):

| 데이터 | 전 | 후 |
|---|---|---|
| ascii | 170 | 299 |
| sync_tui | 167 | 207 |
| dense_cells | 210 | 248 |
| scrolling | 97 | 107 |

실제 앱(테스트 앱: 호스트 프로세스, AppKit, 그리기 포함, 창은 다른 창 뒤, 122×46)으로 3회씩:

| 데이터 | Plum (오늘) | Ghostty 1.4.0 ([11/17](2026-11-17.md)) |
|---|---|---|
| ascii | 199~307 | 254 |
| scrolling | 101~117 | 96 |
| scroll_region | 104~107 | 100 |
| sync_tui | 155~210 | 156 |
| unicode | 203~222 | 197 |
| cursor_motion | 193~226 | 197 |
| dense_cells | 205~266 | 90 |

각 종류의 첫 회가 낮은 것은 준비 운동이다(11/17 측정은 첫 회를 뺐다). 이 표는 날과 조건이 다른 값을 나란히 놓은 것이라, 같은 조건의 비교는 아래에 따로 했다.

## App Nap과 SIGPIPE (11/20 저녁)

- **App Nap.** 창이 다른 창에 가려지면 macOS가 앱을 재워(App Nap) 스레드를 늦춘다. 가려진 테스트 앱에서 출력 처리가 cursor_motion 87~99, ascii 187~214, scroll_region 16~22MB/s였고, 그 앱만 App Nap을 끄자 229~243, 266~322, 108~113MB/s로 돌아왔다. 터미널은 창이 가려진 동안에도 에이전트와 빌드를 돌리므로, 앱이 시작할 때 `ProcessInfo.beginActivity(.userInitiatedAllowingIdleSystemSleep)`로 재우지 말라고 알린다. 쉬는 동안의 CPU는 원래 거의 0이라 늘지 않고, Mac은 그대로 잠자기에 들어갈 수 있다. 창을 최소화해 확인했다(scroll_region 95~110, cursor_motion 209~244, ascii 310~324MB/s).
- **SIGPIPE.** 디버그 명령을 보낸 쪽이 답을 읽기 전에 연결을 닫으면 앱이 흔적 없이 끝났다(종료 코드 141). 커밋된 버전에서도 같았다. 앱도 터미널 호스트처럼 SIGPIPE를 무시해, 그런 쓰기는 EPIPE로 실패하고 지나간다.

## Ghostty 1.4.0과 번갈아 재기 (11/23)

Ghostty 1.4.0 공식판(공증 확인)과 Plum 테스트 앱을 같은 Mac(macOS 26.7.1)에서 같은 데이터로 번갈아 쟀다. 격자 122×46, Menlo 13. Ghostty는 사용자 설정을 읽지 않게 했다. 종류마다 준비 운동 1라운드 뒤 6라운드, 라운드마다 먼저 하는 앱을 바꾸고, 각 실행 전에 1.5초 쉬었다. 차례마다 그 앱을 맨 앞에 가져와 두 앱 모두 그리게 했다(사용자 허락을 받아 그동안 Mac을 쓰지 않았다).

- 라운드 안에서 두 번째로 하는 앱이 느리게 나오는 경향이 있어(앞 앱이 남은 화면을 그리는 중), 라운드마다 두 앱의 비율을 구했다.
- 가끔 시스템 전체가 바빠지는 순간이 한쪽의 차례에 걸리면 그 라운드만 크게 튄다(Plum만 혼자 0.46~0.50, Ghostty만 혼자 비율 2.14). Plum만 2분 동안 70번 재 보니 약 67초 간격으로 그런 순간이 있었다. 그래서 결론은 비율의 중앙값으로 낸다.

| 데이터 | Plum 평균 (MB/s) | Ghostty 평균 (MB/s) | 라운드별 Plum ÷ Ghostty | 중앙값 |
|---|---|---|---|---|
| ascii | 115 / 134 | 108 / 134 | 0.97 1.07 1.19 0.77 1.76 1.03 / 1.08 1.09 0.46 1.10 1.14 1.05 | 1.05× / 1.09× |
| scrolling | 54 | 41 | 1.40 1.21 1.33 1.35 1.22 1.32 | 1.32× |
| scroll_region | 51 / 59 | 51 / 52 | 1.06 1.03 1.08 0.50 1.12 1.16 / 1.18 1.01 1.09 1.28 1.13 1.12 | 1.07× / 1.13× |
| sync_tui | 112 | 95 | 1.14 1.19 1.16 1.15 1.19 1.24 | 1.17× |
| unicode | 152 | 106 | 1.47 1.24 1.22 2.14 1.37 1.53 | 1.42× |
| cursor_motion | 111 | 85 | 1.43 1.26 1.29 1.41 1.29 1.24 | 1.29× |
| dense_cells | 118 | 50 | 2.62 2.67 2.61 0.81 2.69 2.70 | 2.64× |

`/` 뒤는 ascii와 scroll_region만 다시 잰 값이다. 두 앱 모두 그리는 중이라 절대값은 화면 없이 잰 값보다 낮다.

두 앱을 뒤에 두고(창이 가려지면 둘 다 그리지 않는다) 같은 방법으로 잰 것은 다음과 같다(11/20, 중앙값이 아니라 기하평균): ascii 1.13×, scrolling 1.08×, scroll_region 1.10×, sync_tui 1.15×, unicode 1.31×, cursor_motion 1.14×, dense_cells 2.51×. 이때 Ghostty는 가려진 동안 App Nap에 걸린 라운드가 있어(scrolling에서 6~10배 느림) 그런 라운드는 Plum 쪽으로 기운다.

## 바꾼 것

| 무엇 | 어디 | 효과 |
|---|---|---|
| 줄마다 셀을 한 번에 받기 (`ROW_DATA_CELLS_RAW`). 셀의 비트 배치는 라이브러리가 내주는 설명(`ghostty_type_json`)에서 한 번 읽어 직접 푼다. 설명이 없으면 예전처럼 필드마다 묻는다 | `TerminalRenderer.buildRow`, `CellLayout` | 셀당 C 호출 6~8번 → 기본 색 텍스트는 0번 |

| 셀 배치 설명 읽기(약 2ms)를 첫 프레임이 아니라 실행 직후 백그라운드에서 | `AppDelegate` | 첫 프레임 지연 제거 |

## 프레임 비용

새로 만든 `RenderSpeedTests.testFrameCost`. 데이터를 엔진에 넣은 뒤, 모든 줄을 다시 만드는 프레임 400개의 메인 스레드 CPU 시간 평균이다(Menlo 13pt, 2배율). "그리기"는 Metal 명령을 만들어 제출하는 데까지.

| 화면 | 만들기 (전) | 만들기 (후) | 만들기 + 그리기 (후) |
|---|---|---|---|
| ascii | 0.49ms | 0.13ms | 0.36ms |
| dense_cells (셀마다 다른 색) | 0.87ms | 0.33ms | 0.60ms |
| unicode (한글·한자·이모지) | 0.55ms | 0.32ms | 0.54ms |
| sync_tui | 0.30ms | 0.10ms | 0.34ms |

전은 2회, 후는 3회 잰 평균이다. 같은 조건에서 회차 간 차이는 10% 안팎이다.

## 실제 경로: 호스트를 거쳐 읽고 그리기

`RenderSpeedTests.testThroughputWhileDrawing`에 `PLUM_BENCH_HOST=1`. 이 프로세스 안에 터미널 호스트를 띄우고, 프로그램 출력이 호스트의 소켓으로 들어오는 동안 메인 스레드가 화면 밖 Metal 레이어에 최대 120Hz로 그린다. 같은 시간대에 바꾸기 전과 후를 번갈아 5회씩 쟀다(중앙값).

| 데이터 | 처리량 (전 → 후) | 바이트당 CPU (전 → 후) |
|---|---|---|
| ascii | 143 → 171MB/s | 7.60 → 6.81s/GB |
| dense_cells | 173 → 214MB/s | 9.57 → 7.94s/GB |
| unicode | 176 → 194MB/s | 12.76 → 12.59s/GB |
| sync_tui | 157 → 173MB/s | 10.60 → 9.79s/GB |

- unicode의 CPU가 거의 그대로인 것은 처음 보는 글자를 그려 넣는(래스터화) 비용이 대부분이라서다.
- 호스트의 읽기 스레드는 시간의 대부분을 시스템 호출(pty 읽기, 소켓 쓰기, 남은 바이트 확인 `ioctl`)에 쓴다. `ioctl`은 그 스레드의 약 8%인데, 없애려면 pty를 논블로킹으로 바꿔야 하고 큰 붙여넣기에서 입력을 잃을 위험이 있어 두었다.
- 출력이 쏟아질 때 메인 스레드가 프레임을 만들며 기다리는 시간(터미널 잠금 포함)은 평균 0.06ms, 가장 길 때 0.35ms였다. 파싱을 더 잘게 나눌 필요는 없었다.

## 메모리

뒤에 띄운 테스트 앱(창 1180×760pt, 2배율, 탭 7개)으로 쟀다. `footprint` 기준.

| 상태 | 전체 | GPU 드라이버 몫 |
|---|---|---|
| 출력을 계속 그리는 중 | 168MB | 98MB |
| 출력이 멈추고 6초 뒤 | 70MB | 2MB |

- **그리는 동안의 GPU 메모리는 Plum의 것이 아니다.** 창 크기를 800×500으로 줄여도 1600×1000으로 늘려도 98~100MB로 같았다. Metal로 빈 렌더 패스 하나만 그리는 작은 프로그램도 4MB에서 111MB가 됐고, 렌더 패스 대신 컴퓨트 셰이더를 써도 80MB였다. Apple GPU 드라이버가 렌더링 동안 잡는 작업 메모리로 보이고, 출력이 멈추면 시스템이 거둬 간다. 렌더러를 컴퓨트로 다시 짜도 33MB밖에 줄지 않아 하지 않았다.
- **멈춘 뒤 남는 것은 창 크기에 비례한다**(800×500에서 55MB, 1600×1000에서 88MB). 화면에 보이는 터미널이 가진 그리기 버퍼 2개(이미 최소인 2개로 설정되어 있다)와 창 자체다.
- **Plum의 힙은 약 22MB**(탭 7개)다. 큰 것은 SwiftUI·AppKit 내부, Swift 메타데이터, 엔진의 페이지다. 터미널 하나를 만드는 비용은 1MB가 안 된다. 스크롤백은 탭마다 최대 10MB(설정, Ghostty와 같은 기본값)까지 쓴다.
- 쉬는 동안의 CPU는 탭 7개에서 20초에 약 30ms였고, 대부분 2초마다 탭의 프로그램과 포트를 확인하는 시스템 호출이다.

## 다시 재는 법

```sh
python3 bench/gen-data.py <폴더> 122 46        # 약 270MB
PLUM_BENCH_DATA=<폴더> swift test -c release -Xswiftc -enable-testing --filter "RenderSpeedTests/testFrameCost"
PLUM_BENCH_DATA=<폴더> swift test -c release -Xswiftc -enable-testing --filter "PtySpeedTests/testParseSpeed"
PLUM_BENCH_HOST=1 PLUM_BENCH_DATA=<폴더> PLUM_BENCH_RUNS=5 swift test -c release -Xswiftc -enable-testing --filter "RenderSpeedTests/testThroughputWhileDrawing"
```

- `PLUM_BENCH_SETS=ascii,sync_tui`처럼 데이터 종류를 고를 수 있다. 처리량은 시스템 부하에 따라 흔들리므로 바꾸기 전과 후를 같은 시간대에 번갈아 재는 편이 좋다. 프레임 비용과 파싱 속도는 흔들림이 작다.
- 화면 셀 해석이 라이브러리와 맞는지는 `CellLayoutTests`가 매번 확인한다(보통 테스트에 포함).

## 이 측정으로 말할 수 없는 것

- **키 입력 지연, 실행 시간, 메모리의 최신 비교.** 11/23에는 출력 처리량만 Ghostty와 번갈아 쟀다. README의 표는 2026-11-17 값이다.
- **Orca와의 최신 비교.** 하지 않았다.
- **다른 Mac, 1배율 화면.** 2배율 내장 화면 기준의 프레임 비용이다.
