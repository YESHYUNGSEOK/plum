# Plum and Ghostty performance compared, 2026-11-16

Plum 0.1.0 (prototype) and Ghostty 1.3.1 were measured on the same Mac in the same way. The raw data is in `bench/results/20261116-1405/` (session 1) and `bench/results/20261116-1435-followup/` (follow-up), and the measurement scripts are in `bench/`.

> **Read this first: the version compared against.** The Ghostty installed on this Mac is 1.3.1, and that is what Plum was compared with. The latest release at the time of measuring was 1.4.0 (2026-10-27). Plum's terminal engine (libghostty-vt 1.0.1) is built from Ghostty source later than 1.4.0, so **Plum uses a newer Ghostty engine than the Ghostty it was compared with.** The 1.4.0 release notes claim 25–55% faster output than 1.3.x and less GPU memory for hidden tabs. So the gaps below in output throughput and in memory with 10 tabs are likely to shrink against the latest Ghostty. Plum hasn't been compared with 1.4.0 yet. The reasoning is in "Where the differences come from".

## Conclusions

- **Output throughput, key latency and memory**: Plum was better in every condition measured. The differences were larger than the spread between samples, and pointed the same way in every block measured in turns.
- **Launch time**: Plum's window appeared sooner (286ms against 342ms), and Ghostty started the shell a little sooner (239ms against 253ms).
- **Idle CPU**: in undisturbed runs Plum used 1–4ms per 30s. Ghostty used about 290–340ms per 30s in most runs.
- These are measurements from one Mac, one display and one day. The direction and rough size can be trusted more than the numbers themselves.

## Conditions

| Item | Value |
|---|---|
| Machine | MacBook Pro, Apple M4 Pro (8 performance + 4 efficiency cores), 48GB memory, plugged in |
| OS | macOS 26.3.1 |
| Display | Built-in display, 2× scale, 120Hz. Both app windows were on the same display |
| Plum | 0.1.0, release build, font Menlo 13pt, grid 122×46 |
| Ghostty | 1.3.1 (stable, ReleaseFast). No config file. On the command line: font Menlo 13pt, grid 122×46, window state restore off, auto-update off |
| Scrollback | 10MB for both (each one's default) |
| System load | 1-minute load average 1.2–7.8 while measuring. Several security programs and other work kept running |

For fairness:

- The two apps were measured **in turns** (each kind of measurement in the order A, B, B, A). If the system's state changed over time, it didn't work against only one side.
- For every sample, the app being measured was checked to be **in front and visible on screen**, because both apps stop drawing a covered window. Samples that failed the check were thrown out (0 this time in the launch time, output throughput and memory measurements).
- Both apps were measured **from outside, with the same tool**. Plum's internal instrumentation was used only to diagnose idle behavior.
- The first run of each measurement counted as a warm-up and was left out of the totals.

Values in the tables are **median** [Q1–Q3] (min–max).

## Launch time

Time from the moment macOS was asked to launch the app (ms). 15 runs each, after the app had already been launched once.

| Stage | Plum | Ghostty |
|---|---|---|
| Window on screen | **286** [283–289] (254–345) | **342** [322–359] (289–638) |
| Shell process started | **253** [252–256] (222–269) | **239** [224–258] (199–271) |

Plum shows its window first and starts the shell right after; Ghostty starts the shell first and then shows its window. The time until the prompt appears wasn't measured.

## Output throughput

MB/s, computed from the time `cat` took to send a data file. 10 runs per kind, with both apps in front and drawing.

| Data | Contents | Plum | Ghostty | Ratio |
|---|---|---|---|---|
| ascii (100MB) | Plain text in 76-character lines | **114** [113–137] (84–175) | **103** [101–107] (98–115) | 1.11× |
| scrolling (20MB) | Lines of the single letter `y`, repeated | **83** [82–83] (67–84) | **70** [69–72] (69–76) | 1.18× |
| scroll_region (20MB) | Scrolling inside a scroll region | **83** [82–83] (80–85) | **62** [62–62] (61–66) | 1.33× |
| sync_tui (20MB) | 12 lines redrawn in place, like an agent's screen | **117** [116–118] (115–118) | **71** [70–71] (58–74) | 1.66× |
| unicode (30MB) | Korean, Chinese characters, symbols and emoji | **213** [202–220] (167–241) | **125** [124–126] (123–128) | 1.71× |
| cursor_motion (30MB) | Cursor moved to a random position, then one character | **212** [207–214] (143–216) | **111** [110–112] (110–113) | 1.91× |
| dense_cells (50MB) | Every cell with different colors and attributes | **136** [136–137] (127–138) | **60** [60–61] (36–61) | 2.26× |

The data was generated here, following [vtebench](https://github.com/alacritty/vtebench)'s categories (`bench/gen-data.py`; the same arguments give the same bytes). vtebench itself couldn't be used because this Mac has no Rust.

The gap was small for plain text (1.1–1.2×) and grew with more color, cursor movement and Unicode. The closest to a Claude Code screen update is sync_tui.

## Key latency

From the moment a key event was sent to the app to the moment the frame with that character drawn was composited on screen (ms).

**Continuous typing.** Keys pressed 0.12–0.38s apart. Measured in two sessions.

| Session | | Plum | Ghostty |
|---|---|---|---|
| Session 1 | Median | **16.2** [13.3–19.5] (9.6–38.7), 400 presses | **23.5** [18.6–30.1] (14.5–41.3), 400 presses |
| | Mean / 95th percentile | 16.8 / 24.6 | 24.5 / 35.7 |
| Follow-up | Median | **17.0** [14.7–19.4] (10.4–31.4), 300 presses | **28.2** [23.6–33.3] (15.5–45.1), 350 presses |
| | Mean / 95th percentile | 17.3 / 24.3 | 28.4 / 38.5 |

Medians of blocks of 50 presses:

| Session 1 block | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Plum | 13.4 | 14.2 | 13.8 | 13.5 | 18.0 | 19.7 | 18.5 | 18.7 |
| Ghostty | 20.5 | 19.0 | 19.5 | 18.6 | 27.6 | 29.8 | 30.1 | 30.2 |

| Follow-up block | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Plum | 17.9 | 15.7 | 19.6 | 14.7 | 15.0 | 19.3 | — | — |
| Ghostty | — | 26.9 | 28.0 | 27.9 | 31.1 | 28.3 | 28.1 | 26.6 |

In all 13 paired blocks Plum was about 5–16ms lower. From block 4 of session 1, both apps' values went up; the cause wasn't found (presumably a change in the system's state). "—" marks a block thrown out whole because another app came to the front during it.

**First key after a 5s rest.** A key pressed after a long pause.

| | Plum | Ghostty |
|---|---|---|
| Median | **15.7** [12.9–20.6] (11.0–131.8), 48 presses | **21.6** [16.8–24.3] (14.4–32.3), 36 presses |
| Mean / 95th percentile | 19.8 / 29.9 | 21.2 / 28.0 |

Plum's median was lower, but 1 of its 48 presses took 132ms. That fits the hypothesis that Plum, which gives back GPU memory while resting, can occasionally be late when it starts drawing again. With only 1 case it can't be settled.

Method and limits:

- `cat > /dev/null` was left running in the terminal, and number keys were sent. The kernel echoes the characters back (tty echo), so shell settings have no effect.
- On the screen side, the time was the frame display time ScreenCaptureKit reports, and a frame counted when comparing its pixels showed they had actually changed.
- **Keyboard hardware and panel response times aren't included.** The real latency from fingertip to eye is longer, and the extra is the same for both apps.
- Ghostty's cursor blink was turned off for this measurement only (a blink would count as a screen change).

Plum was fixed once while preparing this measurement. In the first trial Plum took 26ms, about a frame slower than Ghostty (20 presses each), and the cause, the Metal layer waiting for display sync (`displaySyncEnabled`), was turned off. All the numbers above are from after the fix.

## Memory

The same value as Activity Monitor's "Memory" (physical footprint). It includes GPU memory counted against the process.

**1 terminal, visible on screen**

| When | Plum (4 runs) | Ghostty (4 runs) |
|---|---|---|
| 10s after launch | **54.8** (54.8–55.0) | **178.4** (91.9–178.9) |
| 60s after launch | **52.0** (51.4–61.5) | **181.1** (85.4–187.0) |
| Peak while running | **158.9** (153.3–164.1) | **199.4** (181.0–203.4) |

- While drawing, both apps hold about 100MB of GPU-side memory. Plum stops drawing when the screen doesn't change, and this memory is given back a few seconds later. So the peaks are similar and the idle values differ.
- In 1 of 4 runs Ghostty was at 85–92MB. Its idle CPU was also close to 0 in that run, so it seems to have stopped drawing. Why only that run did so wasn't found.

**10 terminals.** 10 tabs in one window. 5 runs each.

| | Plum | Ghostty |
|---|---|---|
| With 1 terminal | **54.9** (54.6–57.8) | **178.1** (92.4–178.3) |
| With 10 terminals | **59.1** [59.0–59.4] (58.9–60.3) | **566.0** [483.4–577.4] (481.9–577.8) |
| Per added terminal | about 0.5MB | about 43MB |

Plum is built to keep one set of screen buffers per window, shared by its tabs. The tabs held freshly started shells; as scrollback builds up, each terminal grows by up to 10MB more.

**After heavy output.** Right after the output throughput runs (about 3GB of output per app). 1 run each.

| | Plum | Ghostty |
|---|---|---|
| Memory | 100.8MB | 574.1MB |

## Idle CPU

CPU time used over 30s with 1 terminal open in front (ms).

| Run | Plum | Ghostty (default) | Ghostty (blink off) |
|---|---|---|---|
| Measured | 1.2, 1.2, 32.7, 985.1 | 2.6, 292.6, 293.3, 339.6 | 289.6, 438.8 |

Plum's values were widely spread, so Plum alone was measured 6 more times with its internal instrumentation on.

| Run | CPU (ms/30s) | Frames drawn | Output received (bytes) |
|---|---|---|---|
| 1, 2, 4, 5 | 4.0, 1.3, 1.9, 2.5 | 0 | 0 |
| 3 | 75.5 | 1 | 0 |
| 0 | 194.8 | 76 | 1633 |

- With nothing happening, Plum uses 1–4ms per 30s.
- In run 0, output came into the terminal. The Mac was in use during the measurement, so keys typed for somewhere else seem to have gone into the measurement window in front. The 985ms in the table before likely has the same cause, but that run had no instrumentation, so it wasn't confirmed.
- Run 3 spent 75ms drawing one frame. That looks like the cost of taking back the GPU memory given up while resting.
- Ghostty's value didn't drop with cursor blink off. Blinking isn't the only cause.

## Where the differences come from

To pin down the cause of the output throughput gap, two more things were measured (`bench/results/20261116-drawing-cost/`, `Tests/PlumKitTests/EngineSpeedTests.swift`).

**It isn't drawing.** Compared with the window minimized so nothing is drawn (MB/s, median of 4 runs each).

| Data | Plum drawing | Plum minimized | Ghostty drawing | Ghostty minimized |
|---|---|---|---|---|
| ascii | 114 | 134 | 100 | 106 |
| dense_cells | 156 | 148 | 60 | 62 |
| unicode | 230 | 256 | 125 | 134 |
| cursor_motion | 220 | 253 | 109 | 119 |
| sync_tui | 120 | 130 | 69 | 78 |

Not drawing makes Ghostty only 3–13% faster. The slow part isn't drawing but reading and interpreting the output.

**The engine on its own** (the same data fed straight into libghostty-vt 1.0.1, which Plum uses, with no pty and no drawing; MB/s):

| ascii | scrolling | dense_cells | unicode | cursor_motion | scroll_region | sync_tui |
|---|---|---|---|---|---|---|
| 2203 | 137 | 281 | 705 | 383 | 137 | 199 |

- The engine handles plain text at over 2GB/s, yet both apps stay at 100–134MB/s. The limit here is not the terminal but the pty (the kernel) and `cat`. That's why the two apps differ little on ascii.
- With lots of color and cursor movement, the engine's parsing speed shows. Plum being faster here is **more likely because it uses a newer Ghostty engine** than because Plum does something better. Confirming it needs a comparison with Ghostty 1.4.0.

**Differences that can be put down to Plum's design**

- Key latency: when output arrives, Plum draws right away instead of waiting for the next screen refresh, and hands over the frame without waiting for display sync. That one setting cut Plum's own latency by about 10ms; this was checked directly. Why Ghostty takes about one frame longer wasn't found.
- Idle memory and CPU: when the screen doesn't change, Plum stops drawing entirely.
- Tab memory: all tabs share one set of screen buffers. Ghostty 1.3.1 used about 43MB per tab; 1.4.0 is said to have cut GPU memory for hidden tabs.
- Plum has no ligatures, no image display, no split panes and no configuration system. It does less, and is lighter for it.

## What these measurements don't show

- **A comparison with the latest Ghostty (1.4.0).** As noted above, this is the biggest limit.

- **Results on other Macs and other displays.** Nothing was measured on a 60Hz external monitor or an Intel Mac.
- **How it feels in real work.** The data is synthetic, and a long real Claude Code session wasn't measured.
- **Latency from fingertip to eye.** That needs a high-speed camera.
- **Ghostty tuned through its settings.** Only the defaults were used.
- **Conditions with no interference at all.** Security programs and other work were running, and the Mac was in use. Taking turns and checking each sample reduced the effect but didn't remove it.

## How to measure again

```sh
./scripts/bundle.sh                                   # build/Plum.app
swiftc -O bench/plumbench.swift -o bench/plumbench    # measurement tool
python3 bench/run.py all                              # about 30 minutes. Windows take turns coming to the front
python3 bench/run.py latency_idle idle                # follow-up measurements
python3 bench/summarize.py bench/results/<folder>
```

The terminal app running these scripts needs Accessibility and Screen Recording permissions. Key events go only to the target app's process, but the measurement window takes keyboard focus while measuring, so it's best not to use the Mac meanwhile.
