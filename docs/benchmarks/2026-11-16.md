# Plum과 Ghostty 성능 비교 — 2026-11-16

Plum 0.1.0(프로토타입)과 Ghostty 1.3.1을 같은 Mac에서 같은 방법으로 쟀다. 원자료는 `bench/results/20261116-1405/`(1차)와 `bench/results/20261116-1435-followup/`(보강)에 있고, 측정 스크립트는 `bench/`에 있다.

> **먼저 읽을 것 — 비교 대상의 버전.** 이 Mac에 설치된 Ghostty는 1.3.1이고, 그것과 비교했다. 측정 시점의 최신판은 1.4.0(2026-10-27)이다. Plum의 터미널 엔진(libghostty-vt 1.0.1)은 1.4.0 이후의 Ghostty 소스에서 빌드된 것이라, **Plum은 비교 대상보다 새로운 Ghostty 엔진을 쓰고 있다.** 1.4.0 릴리스 노트는 1.3.x 대비 출력 속도 25~55% 향상과 숨은 탭의 GPU 메모리 감소를 내세운다. 따라서 아래의 출력 속도와 탭 10개 메모리 차이는 최신 Ghostty에서는 줄어들 가능성이 높다. 1.4.0과는 아직 비교하지 않았다. 자세한 근거는 "차이가 어디서 오는가"에 있다.

## 결론

- **출력 처리, 키 입력 지연, 메모리**는 측정한 모든 조건에서 Plum이 나았다. 차이가 표본 간 흩어짐보다 크고, 번갈아 잰 블록마다 방향이 같았다.
- **실행 시간**은 창이 뜨는 시점은 Plum이 빠르고(286ms 대 342ms), 셸이 시작되는 시점은 Ghostty가 조금 빠르다(239ms 대 253ms).
- **유휴 CPU**는 방해받지 않은 실행에서 Plum이 30초에 1~4ms였다. Ghostty는 대부분의 실행에서 30초에 약 290~340ms였다.
- 한 대의 Mac, 한 화면, 하루의 측정이다. 수치 자체보다 방향과 대략의 크기를 믿을 수 있는 수준이다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 기기 | MacBook Pro, Apple M4 Pro (성능 8 + 효율 4코어), 메모리 48GB, 전원 연결 |
| OS | macOS 26.3.1 |
| 화면 | 내장 디스플레이, 2배율, 120Hz. 두 앱 창을 같은 화면에 두었다 |
| Plum | 0.1.0, 릴리스 빌드, 글꼴 Menlo 13pt, 격자 122×46 |
| Ghostty | 1.3.1 (stable, ReleaseFast). 설정 파일 없음. 명령줄로 글꼴 Menlo 13pt, 격자 122×46, 창 상태 복원 끔, 자동 업데이트 끔 |
| 스크롤백 | 둘 다 10MB (각자의 기본값) |
| 시스템 부하 | 측정 중 1분 평균 load 1.2~7.8. 보안 프로그램 여러 개와 다른 작업이 계속 돌고 있었다 |

공정성을 위해 지킨 것:

- 두 앱을 **번갈아** 쟀다(같은 종류의 측정을 A, B, B, A 순으로). 시간에 따라 시스템 상태가 변해도 한쪽에만 불리하지 않다.
- 매 표본마다 대상 앱이 **맨 앞에 있고 화면에 보이는지** 확인했다. 가려진 창은 두 앱 모두 그리기를 멈추기 때문이다. 확인에 실패한 표본은 버렸다(이번에는 실행 시간·출력 속도·메모리 측정에서 0개).
- 두 앱을 **밖에서 같은 도구로** 쟀다. Plum 내부 계측은 유휴 동작 진단에만 썼다.
- 각 측정의 첫 실행은 준비 운동으로 보고 집계에서 뺐다.

표의 값은 **중앙값** [1사분위–3사분위] (최소–최대) 형식이다.

## 실행 시간

macOS에 앱 실행을 요청한 순간부터 잰 시간(ms). 각 15회, 이미 한 번 실행한 뒤의 상태다.

| 구간 | Plum | Ghostty |
|---|---|---|
| 창이 화면에 뜸 | **286** [283–289] (254–345) | **342** [322–359] (289–638) |
| 셸 프로세스 시작 | **253** [252–256] (222–269) | **239** [224–258] (199–271) |

Plum은 창을 먼저 띄운 직후 셸을 시작하고, Ghostty는 셸을 먼저 시작한 뒤 창을 띄운다. 프롬프트가 보이기까지의 시간은 재지 않았다.

## 출력 처리 속도

데이터 파일을 `cat`으로 보내는 데 걸린 시간으로 계산한 MB/s. 종류별 각 10회, 두 앱 모두 맨 앞에서 그리는 상태.

| 데이터 | 내용 | Plum | Ghostty | 배율 |
|---|---|---|---|---|
| ascii (100MB) | 76자 줄의 일반 텍스트 | **114** [113–137] (84–175) | **103** [101–107] (98–115) | 1.11× |
| scrolling (20MB) | `y` 한 글자 줄 반복 | **83** [82–83] (67–84) | **70** [69–72] (69–76) | 1.18× |
| scroll_region (20MB) | 스크롤 영역 안에서 스크롤 | **83** [82–83] (80–85) | **62** [62–62] (61–66) | 1.33× |
| sync_tui (20MB) | 에이전트 화면처럼 12줄을 제자리에서 다시 그림 | **117** [116–118] (115–118) | **71** [70–71] (58–74) | 1.66× |
| unicode (30MB) | 한글·한자·기호·이모지 | **213** [202–220] (167–241) | **125** [124–126] (123–128) | 1.71× |
| cursor_motion (30MB) | 임의 위치로 커서 이동 후 한 글자 | **212** [207–214] (143–216) | **111** [110–112] (110–113) | 1.91× |
| dense_cells (50MB) | 모든 칸의 색과 속성이 다름 | **136** [136–137] (127–138) | **60** [60–61] (36–61) | 2.26× |

데이터는 [vtebench](https://github.com/alacritty/vtebench)의 분류를 따라 직접 생성했다(`bench/gen-data.py`, 같은 인자면 같은 바이트). vtebench 자체는 이 Mac에 Rust가 없어 쓰지 못했다.

일반 텍스트에서는 차이가 작고(1.1~1.2배), 색·커서 이동·유니코드가 많을수록 차이가 커진다. Claude Code 화면 갱신과 가장 비슷한 것은 sync_tui다.

## 키 입력 지연

키 이벤트를 앱에 보낸 시각부터, 그 글자가 그려진 프레임이 화면에 합성된 시각까지(ms).

**연속 입력** — 0.12~0.38초 간격으로 누름. 두 번의 세션으로 쟀다.

| 세션 | | Plum | Ghostty |
|---|---|---|---|
| 1차 | 중앙값 | **16.2** [13.3–19.5] (9.6–38.7), 400회 | **23.5** [18.6–30.1] (14.5–41.3), 400회 |
| | 평균 / 95번째 백분위 | 16.8 / 24.6 | 24.5 / 35.7 |
| 보강 | 중앙값 | **17.0** [14.7–19.4] (10.4–31.4), 300회 | **28.2** [23.6–33.3] (15.5–45.1), 350회 |
| | 평균 / 95번째 백분위 | 17.3 / 24.3 | 28.4 / 38.5 |

50회씩 묶은 블록의 중앙값:

| 1차 블록 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Plum | 13.4 | 14.2 | 13.8 | 13.5 | 18.0 | 19.7 | 18.5 | 18.7 |
| Ghostty | 20.5 | 19.0 | 19.5 | 18.6 | 27.6 | 29.8 | 30.1 | 30.2 |

| 보강 블록 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Plum | 17.9 | 15.7 | 19.6 | 14.7 | 15.0 | 19.3 | — | — |
| Ghostty | — | 26.9 | 28.0 | 27.9 | 31.1 | 28.3 | 28.1 | 26.6 |

짝이 맞는 13개 블록 모두에서 Plum이 약 5~16ms 낮았다. 1차의 4번 블록부터 두 앱 모두 값이 올라갔는데 원인은 확인하지 못했다(시스템 상태 변화로 추정). "—"는 측정 도중 다른 앱이 앞으로 나와 블록 전체를 버린 경우다.

**5초 쉬고 난 첫 키** — 한참 멈췄다가 누르는 경우.

| | Plum | Ghostty |
|---|---|---|
| 중앙값 | **15.7** [12.9–20.6] (11.0–131.8), 48회 | **21.6** [16.8–24.3] (14.4–32.3), 36회 |
| 평균 / 95번째 백분위 | 19.8 / 29.9 | 21.2 / 28.0 |

중앙값은 Plum이 낮지만, Plum에서 48회 중 1회가 132ms였다. Plum은 쉬는 동안 GPU 메모리를 돌려주므로 다시 그리기 시작할 때 드물게 늦어질 수 있다는 가설과 맞지만, 1회뿐이라 단정할 수 없다.

측정 방법과 한계:

- 터미널에서 `cat > /dev/null`을 실행해 두고 숫자 키를 보냈다. 글자를 되돌려 주는 것은 커널(tty 에코)이라 셸 설정의 영향을 받지 않는다.
- 화면 쪽 시각은 ScreenCaptureKit이 알려 주는 프레임 표시 시각을 썼고, 프레임의 픽셀이 실제로 바뀌었는지 비교해 판정했다.
- **키보드 하드웨어와 패널의 응답 시간은 포함되지 않는다.** 손끝에서 눈까지의 실제 지연은 이보다 길고, 그 추가분은 두 앱이 같다.
- Ghostty는 이 측정에서만 커서 깜빡임을 껐다(깜빡임이 화면 변화로 잡히기 때문).

이 측정을 준비하며 Plum을 한 번 고쳤다. 처음 시험에서는 Plum이 26ms로 Ghostty보다 한 프레임쯤 느렸고(각 20회), 원인이던 Metal 레이어의 화면 동기 대기(`displaySyncEnabled`)를 껐다. 위 수치는 모두 고친 뒤의 것이다.

## 메모리

Activity Monitor의 "메모리"와 같은 값(physical footprint)이다. 프로세스 몫으로 잡히는 GPU 메모리를 포함한다.

**터미널 1개, 화면에 보이는 상태**

| 시점 | Plum (4회) | Ghostty (4회) |
|---|---|---|
| 실행 10초 뒤 | **54.8** (54.8–55.0) | **178.4** (91.9–178.9) |
| 실행 60초 뒤 | **52.0** (51.4–61.5) | **181.1** (85.4–187.0) |
| 실행 중 최대 | **158.9** (153.3–164.1) | **199.4** (181.0–203.4) |

- 두 앱 모두 화면을 그리는 동안에는 GPU 쪽 메모리 약 100MB가 잡힌다. Plum은 화면이 바뀌지 않으면 그리기를 멈춰 몇 초 뒤 이 메모리가 반환된다. 그래서 최대값은 비슷하고 유휴 값이 다르다.
- Ghostty는 4회 중 1회에서 85~92MB였다. 그 실행에서는 유휴 CPU도 거의 0이었으니 그리기가 멈춰 있었던 것으로 보인다. 왜 그 실행만 그랬는지는 확인하지 못했다.

**터미널 10개** — 한 창에 탭 10개. 각 5회.

| | Plum | Ghostty |
|---|---|---|
| 터미널 1개일 때 | **54.9** (54.6–57.8) | **178.1** (92.4–178.3) |
| 터미널 10개일 때 | **59.1** [59.0–59.4] (58.9–60.3) | **566.0** [483.4–577.4] (481.9–577.8) |
| 터미널 하나가 늘 때 | 약 0.5MB | 약 43MB |

Plum은 화면 버퍼를 창 하나에 한 벌만 두고 탭끼리 공유하도록 만들었다. 탭은 방금 띄운 셸 상태였고, 스크롤백이 쌓이면 터미널마다 최대 10MB까지 더 는다.

**대량 출력 뒤** — 출력 속도 측정(앱마다 약 3GB 출력)을 마친 직후. 1회씩.

| | Plum | Ghostty |
|---|---|---|
| 메모리 | 100.8MB | 574.1MB |

## 유휴 CPU

터미널 1개를 맨 앞에 띄워 두고 30초 동안 쓴 CPU 시간(ms).

| 실행 | Plum | Ghostty (기본) | Ghostty (깜빡임 끔) |
|---|---|---|---|
| 측정값 | 1.2, 1.2, 32.7, 985.1 | 2.6, 292.6, 293.3, 339.6 | 289.6, 438.8 |

Plum의 값이 크게 흩어져서, Plum만 내부 계측을 켜고 6회 더 쟀다.

| 실행 | CPU (ms/30초) | 그린 프레임 | 받은 출력 (바이트) |
|---|---|---|---|
| 1, 2, 4, 5 | 4.0, 1.3, 1.9, 2.5 | 0 | 0 |
| 3 | 75.5 | 1 | 0 |
| 0 | 194.8 | 76 | 1633 |

- 아무 일도 없으면 Plum은 30초에 1~4ms를 쓴다.
- 0번 실행은 터미널에 출력이 들어왔다. 측정 중 Mac이 사용되고 있었으므로, 다른 곳에 치던 키가 맨 앞에 뜬 측정 창으로 들어간 것으로 보인다. 앞 표의 985ms도 같은 원인일 가능성이 높지만 그 실행에는 계측이 없어 확인하지 못했다.
- 3번 실행은 프레임 한 장을 그리는 데 75ms를 썼다. 쉬는 동안 반환한 GPU 메모리를 다시 잡는 비용으로 보인다.
- Ghostty는 커서 깜빡임을 꺼도 값이 줄지 않았다. 깜빡임만이 원인은 아니다.

## 차이가 어디서 오는가

출력 속도 차이의 원인을 가르려고 두 가지를 더 쟀다(`bench/results/20261116-drawing-cost/`, `Tests/PlumKitTests/EngineSpeedTests.swift`).

**그리기 때문은 아니다.** 창을 최소화해 그리지 않게 한 상태와 비교했다(MB/s, 각 4회 중앙값).

| 데이터 | Plum 그림 | Plum 최소화 | Ghostty 그림 | Ghostty 최소화 |
|---|---|---|---|---|
| ascii | 114 | 134 | 100 | 106 |
| dense_cells | 156 | 148 | 60 | 62 |
| unicode | 230 | 256 | 125 | 134 |
| cursor_motion | 220 | 253 | 109 | 119 |
| sync_tui | 120 | 130 | 69 | 78 |

Ghostty는 그리지 않아도 3~13%만 빨라진다. 느린 구간은 그리기가 아니라 출력을 읽고 해석하는 쪽이다.

**엔진만 따로 돌리면** (pty도 그리기도 없이 Plum이 쓰는 libghostty-vt 1.0.1에 같은 데이터를 직접 넣음, MB/s):

| ascii | scrolling | dense_cells | unicode | cursor_motion | scroll_region | sync_tui |
|---|---|---|---|---|---|---|
| 2203 | 137 | 281 | 705 | 383 | 137 | 199 |

- 일반 텍스트는 엔진이 2GB/s 넘게 처리하는데 두 앱 모두 100~134MB/s에 머문다. 이 구간의 한계는 터미널이 아니라 pty(커널)와 `cat`이다. 그래서 ascii에서는 두 앱의 차이가 작다.
- 색·커서 이동이 많은 데이터에서는 엔진의 해석 속도가 드러난다. 여기서 Plum이 빠른 것은 Plum이 무언가를 더 잘해서라기보다 **더 새로운 Ghostty 엔진을 쓰기 때문일 가능성이 높다.** 확인하려면 Ghostty 1.4.0과 비교해야 한다.

**Plum의 설계에서 온 것으로 볼 수 있는 차이**

- 키 입력 지연: Plum은 출력이 오면 다음 화면 갱신을 기다리지 않고 바로 그리고, 화면 동기를 기다리지 않고 프레임을 넘긴다. 이 설정 하나로 Plum 자신의 지연이 약 10ms 줄어든 것은 직접 확인했다. Ghostty가 왜 한 프레임쯤 더 걸리는지는 확인하지 못했다.
- 유휴 메모리와 CPU: 화면이 바뀌지 않으면 그리기를 완전히 멈춘다.
- 탭 메모리: 화면 버퍼 한 벌을 모든 탭이 같이 쓴다. Ghostty 1.3.1은 탭마다 약 43MB를 썼는데, 1.4.0에서 숨은 탭의 GPU 메모리를 줄였다고 한다.
- Plum에는 글자 모양 조합(리거처), 이미지 표시, 화면 분할, 설정 체계가 없다. 하는 일이 적은 만큼 가볍다.

## 이 측정으로 말할 수 없는 것

- **최신 Ghostty(1.4.0)와의 비교.** 위에 적은 대로 가장 큰 한계다.

- **다른 Mac, 다른 화면에서의 결과.** 60Hz 외장 모니터나 Intel Mac에서는 재지 않았다.
- **실제 작업에서의 체감.** 데이터는 합성한 것이고, Claude Code를 실제로 오래 돌린 상태는 재지 않았다.
- **손끝에서 눈까지의 지연.** 고속 카메라가 필요하다.
- **Ghostty를 설정으로 튜닝했을 때.** 기본 설정만 썼다.
- **방해가 전혀 없는 조건.** 보안 프로그램과 다른 작업이 돌고 있었고, Mac이 사용되는 중이었다. 번갈아 재기와 표본 검사로 영향을 줄였지만 없애지는 못했다.

## 다시 재는 법

```sh
./scripts/bundle.sh                                   # build/Plum.app
swiftc -O bench/plumbench.swift -o bench/plumbench    # 측정 도구
python3 bench/run.py all                              # 약 30분. 창이 번갈아 앞으로 나온다
python3 bench/run.py latency_idle idle                # 보강 측정
python3 bench/summarize.py bench/results/<폴더>
```

터미널 앱(이 스크립트를 실행하는 앱)에 손쉬운 사용과 화면 기록 권한이 있어야 한다. 키 이벤트는 대상 앱 프로세스에만 보내지만, 측정 중에는 측정 창이 키보드 포커스를 가져가므로 Mac을 쓰지 않는 편이 좋다.
