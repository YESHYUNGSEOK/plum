# Plum, Ghostty 1.4.0 and Orca performance compared, 2026-11-17

Plum, the latest Ghostty (1.4.0) and Orca (1.4.259) were measured on the same Mac in the same way. The raw data is in `bench/results/20261117-1238/`, and the measurement scripts are in `bench/`. The previous measurement ([2026-11-16](2026-11-16.md)) compared against Ghostty 1.3.1; this time the comparison is with the latest Ghostty, which that document named as its biggest limit.

## Conclusions

- **Against the latest Ghostty, the results are mixed.** Last time Plum was faster at every kind of output, but Ghostty 1.4.0 handled plain text (ascii) at 2.1× Plum's speed. Ghostty was also 1.2–1.3× faster at scrolling and TUI redraw (sync_tui). Plum was still faster on screens with lots of color and attributes, Unicode and cursor movement (1.07–1.53×).
- **Plum was still better on key latency, memory and idle CPU.** Latency was 18.5ms for Plum and 24.0ms for Ghostty, and Plum was lower in all 8 blocks measured in turns. Memory with 1 terminal was 37MB against 148MB.
- **Orca is in another class.** It's an Electron app (its terminal is xterm.js), and its output throughput was 1/8–1/24 of Plum's. It used about 20× the memory (721MB), took 3.7× as long to show its window (1,050ms), and used about 1s of CPU per 30s while idle. Its key latency was 28.5ms, 10ms longer than Plum's and 4.5ms longer than Ghostty's. Of those three measures, latency is where the gap was smallest.
- These are measurements from one Mac, one external display and one day. The direction and rough size can be trusted more than the numbers.

For fairness (same as last time):

- The three apps were measured **in turns**. The order rotated each round (Plum→Ghostty→Orca, Ghostty→Orca→Plum, …) so that changes in the system over time didn't fall on one app.
- For every sample, the app being measured was checked to be **in front and visible on screen**. Samples that failed the check were thrown out (0 this time).
- All three apps were measured **from outside, with the same tool** (`bench/plumbench`).
- The first run of each measurement counted as a warm-up and was left out of the totals.

Values in the tables are **median** [Q1–Q3] (min–max).

### Choices made for measuring Orca

- **Memory and CPU are the sum over all of Orca's processes**: the main app, renderer, GPU, utility processes, terminal host (`Orca Agents`) and crash reporter. The shells in its terminals and the git, claude and codex that Orca calls aren't Orca, so they were left out. It's the same rule as leaving out Plum's and Ghostty's shells.
- So Orca's "peak memory" is **the sum of each process's peak**. Nothing says the processes peaked at the same moment, so it comes out higher than the real peak.
- Launch time was measured **only to the window appearing**. Orca's first child process is its own helper, not a shell, so "shell started" can't be measured the same way.
- For key latency, a non-blinking cursor (DECSCUSR 2) was set in the terminal. Ghostty's blink was also turned off for this measurement only. Idle CPU and memory were measured with the defaults (blink on).
- With a new profile, Orca finishes onboarding when the first repository is added and **starts the default agent (Claude Code) on its own.** That terminal was closed right away when the measurement profile was made, and later launches were checked to start no agent. Also, the tip bubble shown to first-time users kept blinking a highlight ring, so the key latency condition "press while the screen is still" was hardly ever met. So the tips were turned off in the measurement profile (how: see "How to measure again").

## Output throughput

MB/s, computed from the time `cat` took to send a data file (higher is faster). 10 runs per kind, with the app in front and drawing.

| Data | Plum | Ghostty 1.4.0 | Orca | Plum ÷ Ghostty | Plum ÷ Orca |
|---|---|---|---|---|---|
| ascii (100MB) | **119** [114–135] | **254** [246–256] | **12** [11–12] | 0.47× | 10.4× |
| scrolling (20MB) | **81** [81–81] | **96** [93–97] | **8** [8–8] | 0.84× | 10.1× |
| scroll_region (20MB) | **83** [81–84] | **100** [99–102] | **4** [3–4] | 0.83× | 23.6× |
| sync_tui (20MB) | **119** [117–122] | **156** [147–158] | **9** [9–9] | 0.76× | 12.9× |
| unicode (30MB) | **220** [218–223] | **197** [195–201] | **28** [27–28] | 1.11× | 8.0× |
| cursor_motion (30MB) | **211** [208–214] | **197** [195–197] | **10** [10–10] | 1.07× | 20.8× |
| dense_cells (50MB) | **137** [134–143] | **90** [89–90] | **6** [6–6] | 1.53× | 24.0× |

The data was the same bytes from the same generator as last time (`bench/gen-data.py`). What each kind contains is in [the previous document](2026-11-16.md#output-throughput).

**Ghostty 1.4.0 got much faster.** On the same data, 1.3.1 did ascii 103, sync_tui 71 and dense_cells 60MB/s (previous measurement, different display). That fits the faster output the 1.4.0 release notes describe.

**One explanation in the previous document was wrong.** Last time, with both apps stuck at 100–134MB/s on ascii, it said the limit there was not the terminal but the pty (the kernel) and `cat`. With the same pty and `cat`, Ghostty 1.4.0 does 254MB/s. So **Plum's limit is on Plum's side.** The engine on its own handles ascii at over 2GB/s (previous measurement), and even with the window minimized and nothing drawn Plum did 134MB/s. That points at the path that reads from the pty and hands the bytes to the engine, but **this hasn't been checked yet.** Ghostty is 1.3× faster on sync_tui too, the closest to a Claude Code screen update, so this is what Plum should fix first.

On every kind, Orca was at 1/8–1/24 of Plum and 1/7–1/25 of Ghostty. Its grid is a similar size (108×55, about 6% more cells than Plum's and Ghostty's), so the grid can't explain a gap this large.

| Block | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |

- In all 8 blocks the order was Plum < Ghostty < Orca. The smallest gap between Ghostty and Orca was in block 1 (0.8ms).

- Keyboard hardware and panel response times aren't included. The method is the same as in [the previous document](2026-11-16.md#key-latency).

| 60s after launch (MB) | **37.0** [36.9–37.1] | **147.8** [147.7–147.9] | **148.2** | **721** [717–730] |
| Peak (MB) | **140.3** | **153.8** | **153.5** | **917** (sum of per-process peaks) |

- Plum's idle CPU was 1–3ms per 30s, as last time. It stops drawing when the screen doesn't change.
- Ghostty 1.4.0's idle CPU dropped to 1/3 of 1.3.1's (about 290–340ms). It stayed the same with blink off, so blinking isn't the cause.
- Orca kept using about 1s per 30s, about 3.5% of one core. How much of that is blinking and how much is other work wasn't measured separately.
- Plum's memory being lower than last time (52MB) seems to come from the 1× display, which makes the screen buffers smaller.

## What these measurements don't show

- **Why Plum handles plain text at half the speed of Ghostty 1.4.0.** As noted above, the cause hasn't been checked yet.
- **The latest Orca (1.4.261).** The installed 1.4.259 was measured.
- **Orca slimmed down through its settings.** It was measured with default features such as cursor blink, the usage display and plugins all on.
- **Results on other displays.** This time everything was measured on one external 75Hz display at 1× scale.
- **Latency from fingertip to eye, how it feels in real work, conditions with no interference at all.** The limits in [the previous document](2026-11-16.md#what-these-measurements-dont-show) still apply.

## How to measure again

```sh
./scripts/bundle.sh                                   # build/Plum.app
swiftc -O bench/plumbench.swift -o bench/plumbench    # measurement tool
PLUM_BENCH_GHOSTTY=<path to Ghostty.app> python3 bench/run.py all   # about 50 minutes
python3 bench/summarize.py bench/results/<folder>
```

- Without `PLUM_BENCH_GHOSTTY`, `/Applications/Ghostty.app` is used. The latest release is at <https://ghostty.org/download>.
- Orca is measured only when a measurement profile exists (`PLUM_BENCH_ORCA_HOME`, by default `/private/tmp/plum-bench-orca`). To make one:
  1. Make a git repository `repo` in that folder, and start a separate instance with `open -n -a /Applications/Orca.app --args --user-data-dir=<folder>/data`.
  2. `ORCA_USER_DATA_PATH=<folder>/data orca repo add --path <folder>/repo`. This finishes onboarding and opens an agent terminal, so close every terminal with `orca terminal list` and `orca terminal close`.
  3. Quit Orca, then in the `ui` document of `<folder>/data/profiles/local-default/profile-state.db` set `contextualToursAutoEligible` to `false` and put the repository ids in `setupScriptPromptDismissedRepoIds`. `content_hash` is the SHA-256 of the payload.
- The measurement script force-quits Orca instead of quitting it normally, because a normal quit can install a downloaded update. The Orca not being measured (the one in use) is left alone.
- The terminal app running these scripts needs Accessibility and Screen Recording permissions. While measuring, windows take turns coming to the front and take keyboard focus, so it's best not to use the Mac meanwhile.
